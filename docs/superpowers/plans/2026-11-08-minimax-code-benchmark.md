## 二、MiniMax Code 的实际形态

### 2.1 界面分区

官方描述是「把对话、项目工作区、文件操作、终端、浏览器、技能、记忆和自动化任务放在同一个本地工作环境里」。实际布局可以概括为四块：

| 区域 | MiniMax Code | 说明 |
| --- | --- | --- |
| 左栏 | 会话 / 任务历史 / 项目 | 第三方实测里，每个角色 Agent 有独立条目，点一条进入它的任务 |
| 中栏 | 对话流 + 工具卡 + 计划 + 审批卡 | 主要的「看它干了什么」的地方 |
| 右栏 | 文件 / 变更 / 终端（Coding 模式） | 任务执行中的开发面板；Work 模式隐藏终端等开发面板，减少技术细节 |
| 输入区 | `/` 命令、`+` 菜单、`@` 文件、粘贴图片、Goal 状态 | Goal 发送后，**输入区域上方**出现状态条，可编辑/暂停/继续/清除 |

另外两条形态差异：

- **Coding / Work 双模式**：不是两套产品，而是同一工作区的两种界面与默认工作方式。Coding 保留项目、终端、代码管理；Work 减少技术细节。
- **底部/运行状态行**：显示本轮耗时（`30s`、`9min30s`、`2h9min30s`），Goal 另计累计活跃时间。两者数值可以不同。

### 2.2 任务流：计划 - 执行 - 审阅

**计划。** Plan Mode 用 `/plan on` 开启，`Shift+Tab` 切换。官方明确写了一句关键话：**Plan Mode 只控制规划流程，不改变工具权限**。它适合「目标较大、修改范围不确定、需要先审阅方案」的任务，建议先让 Agent 说明修改范围、风险和验证方法，再决定是否进入修改阶段。

**执行。** 权限模式独立于 Plan Mode，分 Ask / Auto / Full access / Off 四档。执行中按 Enter 会把消息 **steer 给当前 Turn**，按 Alt+Enter 才把后续任务加入 Queue。也就是说，MiniMax 把「打断重来」和「补充一句再继续」拆成了两件事。

**审阅。** 右栏「变更」按文件列出 Agent 的修改，逐文件看 diff，判断接受还是继续改；另有独立的代码审查步骤。更新日志还加了一条「代码变更悬停预览」：鼠标停在文件改动行上就弹 diff，不必打开完整审查面板。

**Goal（长任务）。** Goal 不是「下一步做什么」，而是「最终要做到什么」：设定最终结果、验收证据、工作边界和停止条件；只要未达标、未阻塞、未主动暂停，就继续推进。发送后输入区上方有 Goal 状态，可随时编辑、暂停、继续、清除。官方同时明确它**不适合**终点模糊、主要靠主观判断、一次性短任务与高风险操作。

**Agent Team（并行团队）。** 官方博客强调的是「拆任务、独立验收、关键节点汇报」；第三方实测把它概括成 Leader / Worker / Verifier 三个角色：Leader 拆任务，Worker 执行，Verifier 独立验收。任务有明确状态，关键节点主动汇报。第三方评测原文的描述是「已经完成了 2/5，未完成的 3 个任务中有 2 个已经进入核查阶段」——这句话是整篇材料里对「长任务进度可见性」最直接的证据。

**会话管理。** 支持恢复、搜索、`/fork` 分叉、`/rewind` 回退、`/compact` 压缩上下文、`/transcript` 浏览完整对话、`/export` 导出。

### 2.3 工具与技能的组织方式

官方 FAQ 把两者分得很清楚：

- **技能**：一套写好的专业工作方法，告诉 Agent「先做什么、用哪些工具、如何检查结果」，例如做 PPT、分析数据、设计网页。
- **插件**：增加**可以真正调用的工具和外部服务**，例如飞书、浏览器、数据库；有些插件同时附带技能。

组织方式：

- 技能在输入框用 `/` 触发，可从技能市场安装官方或社区技能，也可自定义；
- 插件有安装、启用、停用、移除的管理入口；
- Subagent 可以集中配置名称、头像、工作指令和模型，并有独立对话入口（更新日志）；
- 模型选择器是独立弹窗，每行模型自带 thinking / context / effort 等能力开关（第一百七十节已解析过其 preload 协议）。

### 2.4 记忆与上下文

官方文档给的是「可见、可编辑、可关闭」三件事：

- 设置 → 个性化 → 记忆：**记忆**（允许使用已保存的记忆）与**主动记忆**（允许主动识别并保存长期有价值的信息）两个开关。
- 关闭记忆后，主动记忆不可调，会话里的记忆入口也隐藏；**关闭开关不会删除已保存的记忆**。
- **记忆摘要**可查看、直接编辑、保存、清空；摘要右上角还能在会话中创建、让 Agent 帮你调整记忆文件。
- 输入框 `/memory` 控制**本次会话**的「使用记忆」与「生成记忆」；「使用记忆」必须在对话开始前设置。
- 该记：沟通偏好、输出格式、项目规则、调试经验、工作流。**不该记**：一次性任务状态、临时日志、敏感密钥、已过期的实现细节。

上下文侧还有：项目规则文件 `AGENTS.md`（`mcode init .` 生成/更新）、`/compact` 压缩长上下文、`/context` 查看占用、`/status` 看运行状态。

### 2.5 diff 与审批的呈现方式

**变更的呈现。** 右栏「变更」按文件列 diff，逐文件判断接受或继续修改；更新日志加了行级悬停预览。这是**按文件、按轮次汇总**的形态，适合代码仓库。

**审批的呈现。** 更新日志写得很具体：Permission 请求改为**完整的审批卡片**，清晰展示**命令、文件、匹配规则和风险**，并区分**单次允许、会话允许与拒绝**；审批会保持打开，**直到 Runtime 确认结果**。权限模式四档（Ask/Auto/Full/Off）决定「什么时候弹卡」。

这套形态的根因是：命令执行有外部副作用、可能长时间运行、结果要等运行时回执。所以它需要「会话允许」来减少重复弹窗，也需要卡片一直挂着直到确认。

## 三、长任务里「用户随时能看懂进行到哪一步」是怎么做到的

这是本次对标最该拆的一节。MiniMax 不是靠一段「请汇报进度」的提示词，而是把进度做进了运行时与界面。可以拆成六条机制：

| 机制 | 具体做法 | 是否结构性 |
| --- | --- | --- |
| 运行状态行 | 当前轮耗时实时走字，Goal 另计累计活跃时间 | 界面 + 运行时时间戳 |
| Goal 状态卡 | 目标常驻在输入区上方，未达标/阻塞/暂停都有明确状态 | 状态机 |
| 任务状态与计数 | Leader 能说出「2/5 完成、2 个在核查」 | 运行时任务表 |
| 关键节点汇报 | 开始、遇到阻塞、需要决策、已完成四类节点主动说话 | 事件 + 汇报策略 |
| 左栏任务历史 | 每个角色/任务一条，点进去看它那一路 | 会话/任务持久化 |
| 远程与通知 | 手机可看进度、补要求、批权限；任务通知卡片 | 跨端，不适用 |

官方博客里有一句方法论，比任何界面细节都重要：

> 新功能不能只靠 prompt 修补，要在 runtime 里加事件、加可观测。

对应到墨宸：**进度必须从既有事件流推导，不能让模型自己写「我完成了 2/5」**。模型自报进度会漂移、会编；事件流不会。

对写长篇小说，一轮任务可以稳定映射成六个阶段：

1. **准备**：收到指令，装配上下文（书、阶段、技能、历史窗口）。
2. **取材**：读章、全书检索、读网页（`read_doc` / `search_docs` / `web_read`）。
3. **起草**：`write_doc` / `propose_patch` 生成提案。
4. **自检**：AI 味闸与确定性检查（已有 `aiFlavorGate`，可扩展）。
5. **待批**：提案卡等人。
6. **写入 / 收尾**：批准后落盘，或本轮结束。

这六段全部能从现有事件（`turn-start`、`tool-call`、提案状态、`turn-end`）推导，不需要新增模型调用，也不需要模型配合。

## 四、可落地结论：搬什么、放哪里、代价多大

| MiniMax 做法 | 墨宸落点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 运行状态行 + Goal 状态 + 任务计数 | 中栏状态行、输入区上方 | 小-中 | **搬，改造**：只做「本轮过程条」，不引入 Goal 自动循环 |
| 关键节点汇报（开始/阻塞/决策/完成） | 状态行、系统通知 | 中 | **部分搬**：桌面端用「待审批 / 失败 / 长轮完成」三类通知 |
| Plan Mode 之后接执行 | 计划块下方一枚「按这个计划执行」 | 小 | **搬**：复用 `prefillComposer` 与既有 workMode 落盘 |
| Verifier 独立验收 | 提案卡上的「交稿前体检清单」 | 中 | **搬原则，不搬团队**：全部复用本地确定性判据，不调模型 |
| 记忆可见、可编辑、可关闭 | 作品资料里的「创作约定」 | 中 | **搬一半**：只做手动维护 + 本会话开关，不做自动提取 |
| 按文件 diff + 悬停预览 | 改稿历史 / 提案卡 | 小 | **不搬**：我们的审批单位是「一处替换」，行内 diff 已比按文件更贴写作 |
| 单次允许 / 会话允许 / 拒绝 | 审批卡 | 中 | **不搬**：与「逐条人审批」铁律冲突；全开档已是唯一放行档 |
| Agent Team 并行 | 六档案 | 大 | **不搬**：主观创作 + token 成本 + 单线程写作，收益不成立 |
| Goal 自动续跑 | 输入区 | 中 | **不搬**：主观质量没有可靠自动验收 |
| 终端 / Git / 浏览器 / 部署 / 云任务 / 定时任务 / 远程控制 | 无 | 大 | **不适用**：纯代码或跨端场景 |

## 五、增量优先级条目（可直接并入现有优先级表）

编号用 `MM-` 前缀，避免与既有 `P0-x`、`F-x` 冲突。每条都写清「改什么 / 为什么 / 涉及模块 / 代价 / 验收 / 不重复」。

### P0-MM-1 本轮过程条：把「现在在哪一步」变成常驻读数

**改什么**

在中栏转录区顶部（或状态行上方）加一条常驻的「本轮过程条」，只读现有事件流：

- 进行中：`阶段 · 当前动作 · 已用时 · 计数`
  例：`起草 · 正在写《第三章》· 4min12s · 已改 2 处 · 待批 1 条`
- 阶段固定六档：`准备 → 取材 → 起草 → 自检 → 待批 → 写入`；没有对应事件就停在当前档，不假装推进。
- 当前动作取**最新一条工具事件**的中文短名（`TOOL_LABELS` 已有）加目标文档名；没有工具事件时显示「思考中」。
- 本轮结束后，过程条自动折叠成一行**轮末小结**：`本轮 6min · 读 3 篇 · 改 2 处 · 自检退回 1 次 · 已写入 1 处 / 待批 1 条`。
- 状态行文案并入阶段，不再只说「工作中 · Ns」。`composeStatusLine` 仍是状态文案的唯一入口，新增阶段入参，组件不另写一套判断。

**为什么**

MiniMax 在长任务里的核心体验不是「能跑很久」，而是「随时问一句就有精确回答」。我们运行中只有 `工作中 · Ns · Esc 打断`（空闲时才报待审/可继续），加上一枚转瞬即逝的「正在思考」；一轮长写作十几分钟，用户切出去再回来，看不出它读了什么、写了几稿、卡在哪。长篇写作一轮的产物是「一章」，比代码任务更需要这条读数。

**涉及模块**

- `apps/desktop/src/renderer/src/utils/timeline.ts`（既有事件块与工具卡）
- 新增 `apps/desktop/src/renderer/src/utils/turn-progress.ts`（阶段与计数的唯一判据）
- `apps/desktop/src/renderer/src/utils/agent-thread.ts`（`composeStatusLine` 增加阶段入参）
- `apps/desktop/src/renderer/src/components/CenterColumn.vue`（状态行与过程条挂线）
- 样式 `apps/desktop/src/renderer/src/styles/agent-pane.css`

**代价**

小-中。纯渲染层，不改 IPC、不改 contracts、不改主进程。需要覆盖三类边界：事件乱序、`turn-end` 后迟到 delta、F-6 事件回放（回放时没有实时工具事件，过程条应显示「回放」而不是假装在跑）。

**验收**

- 一轮含读、写、自检退回、待批的完整轮次，过程条六档按事件顺序推进，不跳档、不倒退。
- 轮末小结的计数与提案卡、工具卡数量一致；没有对应事件时不出现该计数。
- 回放与切书两种情况下不残留上一轮读数。
- `composeStatusLine` 的原有用例全绿，新增阶段用例覆盖「无阶段时退回旧文案」。

**不重复**

状态行已有，但只报耗时与队列；本文补的是**阶段与当前动作**，不是重做状态行。左栏工作项面板（第一百七十四节）已做，不再动。

### P1-MM-2 交稿前体检清单：把「可以交付」摆到批准按钮旁边

**改什么**

在 `ProposalCard.vue` 的 diff 与批准按钮之间加一块紧凑的「体检清单」，只跑本地确定性判据：

- AI 味：复用 `packages/contracts/src/ai-flavor.ts` 的 `aiFlavorGate`，对提案的 `replace` 文本现算。
- 句首重复 / 句式节奏：复用 `sentenceStartRepeat` 与 `sentenceRhythmOf`。
- 字数：复用现有字数统计与章节配额判据；若当前没有独立配额判据，只显示本章字数，不新造阈值。
- 伏笔关键词：若本章有已登记伏笔，复用 `apps/desktop/src/renderer/src/utils/foreshadow.ts` 的判据，只报「本章该回收但没出现」这类确定性问题。

每项只给三态：`通过 / 注意 / 不适用`，附一句人话。**不通过不阻止批准**，但批准按钮旁要写明「有 1 项注意」，并允许用户点开看理由；不静默放行，也不新增二次确认弹窗。

**为什么**

MiniMax 的 Verifier 把「做完了」变成「可以交付了」，且强调独立验收。我们的 AI 味闸已经在写盘前自动退稿，但结果只回到模型，用户在提案卡上看不见；其余检查（伏笔、时间线、人物）要用户自己去右栏点。长篇小说写到二三十章，最大的风险不是单章文笔，而是连续性错误。把确定性检查摆到批准按钮旁边，是成本最低的「独立验收」。

**涉及模块**

- `apps/desktop/src/renderer/src/components/ProposalCard.vue`
- 新增 `apps/desktop/src/renderer/src/utils/proposal-checks.ts`（聚合判据与文案的唯一落点）
- 复用 `packages/contracts/src/ai-flavor.ts`、`apps/desktop/src/renderer/src/utils/foreshadow.ts`
- `apps/desktop/src/renderer/src/styles/agent-pane.css`

**代价**

中。判据全部已有，不新建检查器、不调模型、不改主进程；主要成本在聚合层与提案卡的信息密度控制（不能把卡片堆成一堵墙）。

**验收**

- 一份 AI 味超标的提案，清单显示「注意」并给出命中数；一份干净提案显示「通过」。
- 伏笔未回收只在有登记伏笔时出现；没有登记时显示「不适用」，不编一条假结论。
- 清单不改变批准/拒绝的原有行为，也不新增 IPC。
- 同一判据只有一份：`aiFlavorGate` 等不在组件里重写。

**不重复**

P0-5 已把「审稿」下拉收敛成五个入口，那是**用户主动发起的检查**；本条是**批准前的自动读数**，入口、时机、呈现都不同。AI 味自动退稿闸已有，本条只把它的结果搬到卡上，并补其余确定性判据。

### P1-MM-3 计划转执行：计划不再是一次性输出

**改什么**

`workMode = plan` 的那一轮结束后，在计划正文下方给一枚「按这个计划执行」：

- 点击后把 workMode 切回 act（走既有 `persistMeta` 落盘），并用 `prefillComposer` 预填一句「按上面这份计划执行，先说明你要动的第一处」。
- **不自动发送**，用户仍可改这句再发。
- 计划正文留在上一轮历史里，模型下一轮天然能看到，不新增「计划注入」通道。

**为什么**

MiniMax 的产品主线是 plan → execute → review，Plan Mode 只是这条线的前半段。我们已有「先计划后动手」的闸（批次 4-①），但计划批完就断了：用户要自己重述「照这个做」。补这一枚按钮，把两段接成一条线，成本极低。

**涉及模块**

- `apps/desktop/src/renderer/src/components/CenterColumn.vue`（计划块与按钮）
- `apps/desktop/src/renderer/src/stores/useAgentStore.ts`（`prefillComposer` 已有）
- `apps/desktop/src/renderer/src/stores/useBookStore.ts`（workMode 落盘已有）
- 计划块的判定若已有工具函数，继续用它，不另写

**代价**

小。渲染层 + 既有预填/落盘通路，无新 IPC、无契约改动。

**验收**

- plan 轮结束后按钮出现；act 轮不出现。
- 点击后 workMode 落盘为 act，输入框预填且**未自动发送**。
- 输入框已有字时走 `prefillComposer` 的「不覆盖」分支，给中文提示。
- 计划未生成或本轮失败时按钮不出现。

**不重复**

批次 4-① 做的是「先计划后动手」的闸；本条只做「计划已出、转执行」的交接，不重做闸，也不改计划提示词。

### P2-MM-4 长任务关键节点通知：离开窗口也知道结果

**改什么**

在三类节点发系统通知，点击回到对应章节线程：

- 本轮结束且耗时超过阈值（建议 120 秒）时，且窗口失焦；
- 产生新的待审批提案时，且窗口失焦；
- 本轮失败时，且窗口失焦。

设置页给一个总开关，默认开；同一轮只发一次，不叠加。窗口在前台时只走现有提示，不弹系统通知。

**为什么**

MiniMax 的远程控制本质是「不必盯着」。桌面写作时用户会切去查资料、看参考书；一轮长任务结束时如果没有任何外部提示，用户回来只能翻记录。主进程已有 `Notification` 依赖，成本可控。

**涉及模块**

- `apps/desktop/src/main/agent-service.ts`（事件落点）
- `apps/desktop/src/main/index.ts`（窗口焦点与 `Notification`）
- `apps/desktop/src/renderer/src/stores/useAgentStore.ts`（跳转目标）
- 设置页开关（持久化沿用现有偏好通路）

**代价**

中。跨主/渲染两层，需处理窗口焦点、去重、点击跳转与开关关闭后的静默。

**验收**

- 窗口失焦 + 长轮结束 → 一条通知，点击回到那一章。
- 窗口前台 → 不发系统通知。
- 同一轮多次事件只发一条；开关关闭后一条都不发。
- 通知失败不影响主流程，不抛错。

**不重复**

现有通知只用于更新与少量提示，没有「Agent 长任务节点」这一路。

### P2-MM-5 长对话轮次导航：几十轮里能跳

**改什么**

在 AgentTimeline 右侧加一条细轨道（或顶部下拉），列出本轮次的编号与一句话摘要（例如「第 3 轮 · 起草」），点击滚动定位；当前可见轮次高亮。数据复用既有 `turnAnchors` 与 `cardTurnLabel`。

**为什么**

MiniMax 更新日志专门加了「长对话快速跳转到目标轮次」。我们的 `turnAnchors` 早就在，但用户只能滚。一章写十几轮后，回看「上一版为什么被退回」非常费劲。

**涉及模块**

- `apps/desktop/src/renderer/src/utils/timeline.ts`（锚点已有）
- `apps/desktop/src/renderer/src/components/AgentTimeline.vue`
- 样式 `agent-pane.css`

**代价**

小。纯渲染层，复用锚点；不解决回放跳号（那是 F-6 已知边界，本条不碰）。

**验收**

- 锚点数量与轮次一致；点击滚动到对应轮。
- 当前轮高亮随滚动更新。
- 回放场景下不崩；若锚点缺失则该轮不进轨道，不编空条目。

**不重复**

`turnAnchors` 是防回放丢锚的既有防御，本条只加导航，不改锚点生成规则。

### P2-MM-6 本书记忆：创作约定（可见、可编辑、可关闭）

**改什么**

在作品资料里加一格「创作约定」，不是世界设定，也不是正文：

- 内容是一份**手动维护**的短文本：本书已拍板的取舍、口味、禁区（例如「不写重生」「每章结尾留钩子」「主角不能死」）。
- 落盘走 `book.json` 的可选字段（沿用既有 `persistMeta`），老书没有该字段照常打开。
- 装配时作为一段固定上下文注入（接 `prompt-assembly` 既有装配点），并标明「这是作者的约定，不是世界设定」。
- 输入区 `/memory` 只给一个本会话开关：本次是否使用这份约定；默认使用，可关，关了不影响盘上内容。
- **不做自动提取、不做主动记忆、不做摘要生成**。

**为什么**

MiniMax 记忆最值得抄的是三件事：可见、可编辑、可关闭。自动记忆本身对长篇创作风险很高：一句错记的「主角已死」会污染后续几十章。手动维护的约定则没有这个风险，而且补上了当前的真实缺口——作者在对话里拍板的取舍，开新会话就丢。

**涉及模块**

- `packages/contracts/src/book.ts`（`BookMeta` 可选字段与 zod）
- `packages/fs-store/src/book-meta.ts`（读写与默认值）
- `apps/desktop/src/main/prompt-assembly.ts`（装配）
- `apps/desktop/src/renderer/src/stores/useBookStore.ts`（写盘走 `persistMeta`）
- 作品资料面板 + `ComposerBox.vue`（`/memory` 开关）

**代价**

中。跨 contracts / fs-store / 主进程 / 渲染层，但每一层都有现成通路；没有新的 IPC 通道。

**验收**

- 老书（无该字段）打开正常，约定为空，装配不报错。
- 写入后重开书仍在；关闭本会话开关后装配里没有这段，盘上内容不变。
- 约定与世界设定（故事设定面板）互不覆盖；界面上写清两者边界。
- 不新增自动写入路径。

**不重复**

故事设定（世界观/角色/地点）与作品资料已存在，本条只补「作者的约定」这一类，且明确不碰设定。

## 七、MiniMax 有、但对我们不适用

| 项 | 不适用理由 |
| --- | --- |
| 终端面板 | 纯代码场景；墨宸的产物是文稿，没有命令输出可看 |
| Git / worktree / 变更提交 | 我们没有版本库概念；改稿历史已解决「改坏了怎么办」 |
| 内置浏览器 / 页面预览 / 部署 | 不产出网页；预览没有对象 |
| 按文件审查 diff | 我们的审批单位是「一处替换」，按文件反而丢失上下文；行内 diff 更适合改稿 |
| 变更悬停预览 | 提案卡已经把 diff 摊开；再加一层悬停是重复交互 |
| 单次/会话允许 | 与「逐条人审批」铁律冲突；「全开」档已经是唯一放行档，再加会话级放行会让审批边界变模糊 |
| 审批卡保持到 Runtime 确认 | 本地同步写盘，回执毫秒级；没有远端运行时需要等，这套形态是为命令执行设计的 |
| Agent Team 并行（Leader/Worker/Verifier） | 网文是单线程创作；并行会成倍烧 token，且主观质量无法靠多 Agent 投票解决。只借「独立验收」的原则（见 MM-2），不做团队 |
| Goal 自动续跑 | 主观创作没有可靠的自动验收标准，官方文档自己也不建议用于主观判断；自动续跑容易产出套路化章节 |
| 主动记忆 / 自动摘要 | 长篇 canon 容错极低，错记一句会污染几十章；只做手动约定（MM-6） |
| Remote Control / 移动端 / 云任务接管 | 桌面单机产品，不做跨端 |
| 定时任务 | 写作不是日报；若做提醒是另一个产品线 |
| 无限画布 / 视频生成 / 金融数据 | 与写作工具无关 |
| Subagent 独立对话入口 | 我们的线程按文稿组织，不按档案组织；再加一套入口会造第二个「会话」概念 |

### 7.1 补记（2026-11-21）：「模型行内 thinking/context/effort 开关」这一条**已改判**

这一条原先写在上面那张表里，理由是「上游 `/models` 不提供这些能力位，硬做就是编」（第一百七十节已定案）。
**2026-11-21 用户裁定要补这一块**，实现时把数据来源换掉了，所以那一行从「不适用」挪到「已做」：

- **数据来源不是上游 `/models`，是本仓自己的「模型能力表」**（`packages/contracts/src/model-capability.ts`）。
  那一表是**对着厂商官方文档逐条抄的事实集**（MiniMax / 阿里云百炼 / 智谱 / 小米 MiMo / DeepSeek /
  Google Gemini / OpenAI / OpenRouter 各家的上下文窗口与思考档位，每格带出处 URL）。
  表里没有的模型一律走通用口径——那是「按最常见的那套办」，不是对这个模型的断言。
- **界面形态照 MiniMax Code**：模型列表 + 一块「当前模型的能力」（上下文窗口 / 推理等级两枚），
  而不是把能力摊在名单每一行上（名单里几十个模型，生效的只有一个）。
- **粒度照用户裁定**：上下文窗口与推理等级都挂在**模型（档案）**上，不是连接、不是全局。
- **查证过程中挖出一条比界面更要紧的事实**：本仓只发 `reasoning_effort`，而**只有一部分模型认它**——
  百炼用 `enable_thinking`、智谱与 MiMo 用 `thinking.type`、gpt-4o 根本不是推理模型、
  OpenRouter 的 claude-sonnet-4.5 用 `reasoning.effort`（不是顶层那个）。
  ⇒ 能力表里这些模型的档位集合是**空数组**，界面上那一枚据此置灰并说明原因，
  而不是摆一个按下去没反应的东西。

这也是「照搬 MiniMax Code」这条路第一次**改了形状才搬得动**：不是那套 UI 搬不动，
是那份数据的上游给不出来——**换一份有出处的数据，搬得动**。

## 八、一句话结论

MiniMax Code 的长任务体验之所以「看得懂」，不是因为界面元素多，而是因为**运行时把任务拆成了有状态的小步，界面只读这些状态**。墨宸要补的第一件事不是 Agent Team，而是一条从事件流推导出来的「本轮过程条」；第二件是把已有的确定性检查搬到批准按钮旁边。其余代码场景的终端、Git、远程与并行团队，明确不搬。
