## Description

本仓库是「墨宸 AI」——**用 AI 写小说的本地桌面工作台**。主线只有一条：**读稿 → 提案 → 批准 → 落盘**，对话只是驱动这条线的输入方式，不是产品本身。

这条规则约束界面与交互的取舍：当一份改动能同时"更像大厂聊天产品"和"更快写完稿子"时，按后者判。

## Rule

1. WHEN 评估一个界面或交互能力，THEN the 贡献者 MUST 以「稿子能不能往前走」为判据（写稿 / 审稿 / 交稿三段），而不是以「和通用聊天壳比完备度」为判据。Applies to `apps/desktop/src/renderer/**`.
2. IF 一个能力只服务于「聊得更顺手」而不服务于「稿子往前走」，THEN the 贡献者 MUST NOT 把它排在同等成本的写稿主线能力之前。Applies to 优先级排序.
3. WHEN 借鉴外部产品设计，THEN the 贡献者 MUST 以写作向参照为准（Obsidian / VS Code 编辑器 / Typora / Scrivener / 校阅工具 / 写作平台），纯对话产品（ChatGPT / Claude 的聊天壳）只作交互通用件参照。Applies to 设计借鉴.
4. IF 一项改动动到「提案审批 / 落盘 / 读数 / 交稿体检」其中一段，THEN the 贡献者 MUST 保证该段的动作可回溯、失败可见、不静默丢稿。Applies to `apps/desktop/src/renderer/**`, `apps/desktop/src/main/**`.
5. WHEN 为写稿主线加读数或读条，THEN the 贡献者 MUST 让它常驻在写稿时看得见的地方，而不是只在「刚开始一轮对话时」出现。Applies to `apps/desktop/src/renderer/**`.

## Rationale

这个产品最省事、也最容易走偏的方向是"把它做成一个更好的聊天框"——聊天框的成熟参照最多、最容易抄。但用户买的是稿子，不是回话：一条小说的产出靠"AI 提一条改稿提案、人读完批准、稿子落盘"这个循环跑很多遍，每一遍的摩擦都直接乘以遍数。

聊天壳上最有名的几件东西（消息级"赞/踩"、"重新生成"、拖文件进对话框）在这个产品里恰好不痛：AI 的产出是提案不是答案，重新生成的收益远低于"重跑一次检查"；作者的素材来自书内的素材库/人物卡/伏笔台账（有专门的挂入机制），不是从文件夹拖文件。反过来，写稿时真正会卡住的几处——上下文还能塞多少、这轮被打断了怎么接、右栏体检入口每次重摆、几十章里找一章——在通用聊天产品里根本不存在对应物。

## Examples

### Good

```ts
// 上下文占用常驻在输入卡的工具行：长会话写稿时，"这一轮还塞得下多少"是写作安全感
<ContextMeter />  // 从绑定条搬出来，与模型 chip 同排
```

```ts
// 打断/失败后给一条真出口，而不是让状态行写「可点「继续」」却无处可点
<button @click="resumeTurn()">继续</button>
```

### Bad

```vue
<!-- 把对话区做成信息流：点赞、踩、重新生成、无限滚动 -->
<!-- 聊天壳的功能，不是写稿主线的能力 -->
```

```vue
<!-- 读数只在「这一格还没有消息」时出现：写稿恰恰是开始对话之后才需要它 -->
<ContextBar v-if="hasBook && threadEmpty" />
```

## Exceptions

- 对话区仍然要可用：模型有时只是回答问题（问设定、问写法）。但它是**入口**，不是主界面。
- 纯审美性的取舍（皮肤、动效、留白）不进这条规则的判据，只按"长时间写作是否舒服"看，不按"像不像大厂"看。

## Enforcement

- `manual review` — 新增界面能力时，PR 描述里答一句"它让稿子哪一段更快了"。
- `manual review` — 交稿体检 / 提案审批 / 落盘这三段的改动，必须有真机截图或读数对比。
